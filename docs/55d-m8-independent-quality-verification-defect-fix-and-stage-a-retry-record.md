## 4. 缺陷定位与修复

### 4.1 第一处：深度派生硬绑定首套配方

```text
backend/tests/mixed_bot_validation.py  fixture_at_depth
  修复前：baseline = build_node(...)                       # 只认首套配方
  修复后：baseline = _rebuild_fixture(fixture)              # 按标识归属分派
```

新增 `_rebuild_fixture`：按节点标识形状判定归属的配方集——`{类别}-n{人数}` → 首套，`{类别}-n{人数}-iqv1` → 第二套，**其他形状一律显式失败**。第二套节点的成本矩阵按深度派生因此可用；首套节点行为逐字不变。

### 4.2 第二处：补算排期退回首套口径

```text
backend/tests/mixed_bot_recheck.py  recheck
  修复前：schedule = adversarial_schedule(receipt.stage)    # 退回四族 + 四旧种子
  修复后：schedule = receipt_schedule(receipt.stage, receipt.matches.seed_blocks, receipt.matches.rows)
```

新增 `receipt_schedule`：**种子块取回执记录的主种子，对手族序取逐手行的首次出现顺序**。补算因此按回执自身内容重建排期，既支持第二套清单，又不新增命令行开关；既有四种子回执的行为逐字不变。

同时 `adversarial_schedule` 增可选 `families`（显式族序列优先于族集名称），空序列显式失败。

## 8. 阶段 B 耗时估算

### 8.1 方法

以两次阶段 A 的**真实读数**之差先估出单手的对抗对照耗时，再把 v5 阶段 B 拆成「对抗部分 + 非对抗部分」，最后按第二套规模（对抗 16,896 手）重组。

```text
单手对抗耗时 ≈ (v6 阶段 A 1.981s − v5 阶段 A 0.937s) / (128 − 64) = 0.016313 s/手
v5 阶段 B 的对抗部分   ≈ 4,224 × 0.016313 = 68.9 s
v5 阶段 B 的非对抗部分 ≈ 125.325 − 68.9   = 56.4 s
v6 阶段 B 组件估算     ≈ 56.4 + 16,896 × 0.016313 = 332.0 s ≈ 5.53 分钟
v6 阶段 B 等比估算     ≈ 125.325 × (1.981 / 0.937) = 265.0 s ≈ 4.42 分钟
```

### 8.2 估算结果（**估算，不是读数**）

| 项 | 估算 |
|---|---|
| 阶段 B wall | **约 265–332 s（4.4–5.5 分钟）**，约为 v5 阶段 B（125.3 s）的 **2.1–2.65 倍** |
| 阶段 A + B 累计 | 约 267–334 s，**远低于既有的 ≤1800 s 包络** |
| 阶段 B RSS | 无可靠外推依据：v5 阶段 B 的 `72.2 MiB` 本身相对 v4 已 +19% 且**未归因**；v6 阶段 A 为 `41.0 MiB`（v5 阶段 A 为 `40.7 MiB`）。**只能如实标注为未知，运行中必须实测并监控 ≤100 MiB 包络** |
| 阶段 B 输出大小 | 逐手行由 `4,224` 增至 `16,896`（4 倍），输出粗估为 **4–5 MB 量级**，远低于包络；该数字是粗估 |
| `>=100 ms` 决策 | 阶段 A 实测 `0` 次（p99 `0.553 ms`、max `0.765 ms`）；阶段 B 的建议样本为 `80,000` 次，**不因此推定必然满足** |

### 8.3 估算的已知薄弱处（必须一并记账）

1. 单手对抗耗时由**两次阶段 A 之差**推得，两次运行相隔不久但代码不同、机器状态不同，**不是同一实验的对照**；
2. 两种估算相差 67 s（约 25%），说明该方法本身有量级可观的不确定性；
3. `docs/54h` 已有「估算偏差 41%」的先例：**估算不是读数**；
4. 8 人桌与深筹码路径的决策成本在阶段 A 中被覆盖，但仍不足以排除阶段 B 出现更慢的路径。

**因此：只有阶段 B 的实测 wall/RSS 才是成本读数；本节数字不得作为验收依据。**
