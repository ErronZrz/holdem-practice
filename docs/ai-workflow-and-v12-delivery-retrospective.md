## 1. 背景：原双对话工作流的瓶颈诊断

在 `74` 战役的前半程（`74`、`74a`–`74ay`，共 52 份文档），项目采用的是**双窗口人工衔接工作流**：在 Cursor 中同时开启「裁定员」与「执行者」两个对话，由开发者手动复制两边输出进行传话，并在上下文拥挤时生成近万字的 handoff prompt 开启新对话。

该模式在实践中暴露出两大核心瓶颈：

1. **人工充当消息总线的切换成本**：开发者必须在两个对话窗口之间高频复制「审查结论 / 授权指令」与「执行报告」，大量精力消耗在流程搬运而非产品目标本身。
2. **内部技术门禁泛滥与「五段式公文拆分」**：
   - 由于历史 handoff 提示词中写死了*「提案只列选项不选定」「不替用户选定锁定文本的取舍」「未经显式授权不得改代码或跑测试」*，导致大量纯属验证器内部会计口径、数据结构自洽性的技术细节（如 `74az` 中 `G-20` 在版本 3 上的读法）也被包装成几百行的甲/乙/丙选择题交由用户拍板。
   - 每一个子问题都不得不走完「提案稿 → 审查 → 人工选定 → 锁定文本送审稿 → 审查生效 → 实现方案提案 → 代码落地 → 实现复审」共 5～8 个来回，导致历经 52 份文档仍停留在前置核验（步骤 ③），迟迟未能推进到 Bot 策略本身的改造。

## 2. 辩证复盘：前期「慢阶段」带来的四大核心资产

优化工作流后，`74az`–`74bh` 仅用 **8 个对话轮次**就完成了剩余前置核验闭合与 `@9` → `@12` 四代 Bot 的迭代定型。但复盘 Git 历史可以明确一个关键结论：**后期的极速推进并非否定了前期的积累，而是直接建立在前期「慢阶段」打下的四大工程与方法论资产之上**：

### 2.1 资产一：可精确归因的科学实验基建（分布观测 + 同种子分域配对）

普通 AI 辅助调参最容易陷入「改参数 → 跑几百手撞大运赢了 → 误以为改好」的陷阱。前期慢阶段建立的两项基础设施彻底解决了归因难题：
- **统一分布观测契约（`74b`–`74d`）**：强制策略暴露与实时采样同源、以 `10,000` 整数单位表示的精确离散分布，且查询不污染行动随机流。这使得 `@9`–`@12` 每一次改动都能在 125 个冻结节点上进行逐节点、逐风格、精确到 `0.01%` 的确定性回归，第一时间确认是否误伤无关局面。
- **主随机值 + HMAC-SHA256 域分隔派生（`74r`–`74av`）**：将发牌（`deal`）、非被测座位（`non_probed`）与被测座位（`arm_m` / `arm_b`）的随机源严格解耦，解决了两臂分叉后公开投影不同导致预注册查表失效的问题。正因如此，在 `@10`、`@11`、`@12` 的迭代中，Executor 能够对 4224 对配对做**跨版本逐手差分解剖**（例如直接定位到「版本间差额来自哪几手牌、哪个种子、哪条街的哪个尺度选择」）。

### 2.2 资产二：认知诚实性（Epistemic Honesty）与防作弊护栏

在多轮严苛审查中形成的文档与测试纪律，有效防止了 AI 模型常见的「迎合式作弊」：
- **策略身份不可变与配置摘要锁死**：每次改动必须注册新身份（`@9`、`@10`、`@11`、`@12`）并绑定独立的 SHA-256 配置摘要，旧版本（`@1`–`@8`）的规则、分布与单元测试一字不改，杜绝了「静默修改旧策略掩盖退步」。
- **强制披露负向移动与统计限制**：即便在工作流大幅提速后，`74bd`–`74bh` 依然严格遵循「同时报告变好与变差切片、明确区分单手大底池方差与长期胜率、严禁将有限机械探针或开发标定吹嘘为 Nash / exploitability / 正式不劣化证明」的诚实口径。

### 2.3 资产三：AST 静态架构铁笼（`AGENTS.md` + `74p` 结构断言）

前期在测试集中落地的 AST 源码结构扫描断言，从机械层面锁死了模块依赖边界（`poker/` 不依赖 `api/` 与 `llm/`、`strategy/` 仅通过 `GameState` 行动者安全投影交互、`verification/` 绝不包含推进牌局的可执行代码）。这层自动化「铁笼子」保证了向 Executor 下放技术决策权时不会发生架构腐化或偷看底牌等越界行为。

### 2.4 资产四：`docs/59` 确立的反例驱动改造方法论

`docs/59` 总结的「不直接对着验证阈值调常量、不盲目死磕多人完整 CFR、先用固定反例定位机制再做局部受控改造」为 `@9`–`@12` 提供了清晰的行动指南。

> **核心经验总结**：前期的慢，**有价值的部分在于「数学与工程底座、防作弊护栏、反例驱动方法论」**；**无价值的损耗在于「把人工传话当总线、把五段式公文审批当成内部技术细节的必经门禁」**。工作流改进的本质是**保留前者、砍掉后者**。

## 3. 新工作流架构与 Cursor 工程实践发现

围绕 `.tmp/1014-gpt-suggestion.md` 的思路，本项目落地并验证了基于 Cursor 原生能力的 **Orchestrator + Executor + Reviewer Subagent** 闭环工作流（固化于 `.cursor/rules/ai-workflow.mdc`）。实践中的关键技术发现如下：

### 3.1 单窗口双模型编排与 `resume` 会话连续性

- **分工配置**：
  - **主对话（Orchestrator + Executor）**：在 Cursor `Agent` 模式下选用 **Grok 4.7**，负责阅读任务简报、自主做出内部技术与策略机制裁定、编写代码与测试、运行检查命令，并调度子 Agent。
  - **独立审查子 Agent（Reviewer Subagent）**：主对话通过内置 `Task` 工具同步调用 **Gemini 4 Argon**（传入 `subagent_type="generalPurpose"`, `model="gemini-4-argon-high"`），以只读方式独立核验需求文档、`AGENTS.md`、源码与 `git diff`，输出结构化的 `VERDICT: PASS / FAIL`。
- **`resume` 连续性实测**：
  - 证实 Cursor `Task` 工具原生支持通过 `resume="<agent_id>"` 稳定恢复同一个 Reviewer Subagent。在 `74az`–`74bh` 的连续 6 个任务中，每个任务均由首次创建的 Reviewer 完成首审，修复或确认后通过 `resume` 恢复同一 Subagent 完成第二轮复核（最先在 `.tmp/review-log.md` 登记 ID），彻底消除了人工跨窗口复制。

### 3.2 决策分级授权与反公文化

- **内部技术决策全权委托**：凡属验证器内部口径、判据读法、数据结构绑定、测试断言、反例脚本与策略内部机制微调，只要不违反 `AGENTS.md` 与 `docs/59` 护栏，均由 Executor 直接拍板并经 Reviewer 复核，**将原本需要 5～8 份文档的流程压缩为 1 份合并记录文档**。
- **人工介入仅限三类节点**：
  1. 涉及 Bot 玩法定位或是否继续迭代 vs 收官切换的路线级决策；
  2. 连续 3 轮 Reviewer 审查仍无法收敛的重大冲突；
  3. 里程碑闭环后的汇报与 `git commit` + `git push` 确认。
- **交互规范**：禁用 Cursor 的 `AskQuestion` 弹窗工具，所有待确认事项一律使用普通 Markdown 列表直接呈现。

### 3.3 Cursor 权限、沙箱与免审批推送机制的排查发现

在落地自动化过程中，排查并解决了三个具有普遍参考价值的 Cursor 机制问题：

1. **为什么 `Command Allowlist` 中已有 `git push`，执行 `git push origin master` 仍会弹窗？**
   - **原因**：在 `Auto-Review (with Sandbox)` 模式下，`git push` 需要请求沙箱提权（`required_permissions: ["git_write", "full_network"]`）。凡是申请跳出默认沙箱边界的命令都会被送交后台的 Auto-Review 分类器（Smart Mode Classifier）。当命令中显式带有主干分支名 `origin master`，而用户当轮提示词只写了“允许 push”未点名 `master` 时，分类器会以*「直接推送到受保护的 master 分支需要显式用户意图」*为由拦截。
   - **解法**：① 在 `.cursor/permissions.json` 中配置 `autoRun.allow_instructions` 明确声明允许 `git commit` 与 `git push`；② 在工作流规则中指示 Agent 在已配置上游追踪分支时优先执行不带分支参数的 `git push`。实测此后推送均一次直接通过。
2. **为什么修改 `.cursor/permissions.json` 后偶发一次 `Unauthorized` 中断？**
   - **原因**：`.cursor/permissions.json` 属于 IDE 权限策略文件，写入后触发 Cursor 客户端热重载权限上下文，导致当轮流式输出尾段被截断，但底层 Shell 命令本身已执行完毕。
3. **为什么 Agent 每次提交前都要跑命令确认 `.tmp` 已被忽略？**
   - **原因**：`.tmp/` 最初仅在本地全局忽略中，未写入仓库 `.gitignore`，导致新对话 Agent 每次看到根目录下的 `.tmp/` 都会谨慎调用 `git check-ignore`。
   - **解法**：将 `.tmp/` 显式写入仓库 `.gitignore`，并在 `.cursor/rules/ai-workflow.mdc` 中明令禁止运行忽略性核验命令。

### 3.4 跨对话无损接力机制（`task-brief.md` 队列纪律）

- **问题**：当单个对话完成阶段任务并提交后，若将 `.tmp/task-brief.md` 的 `## 4. 下一步计划` 改写为「等待用户的下一步指示」，会导致下一个新对话使用通用启动词进入时回答「暂无明确的下一步计划」。
- **解法**：在 `.cursor/rules/ai-workflow.mdc` 中确立硬性纪律——更新 `.tmp/task-brief.md` 时，已完成项移入 `§3 当前仓库与进展`，而 `§4 下一步计划` **必须始终维护朝向最终目标的具体待执行步骤队列**。由此实现了所有新对话仅需粘贴同一段通用提示词即可无缝接力。
