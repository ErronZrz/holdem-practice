## 5. 结论

1. **未观察到任何「不同值」差异。** 343 手中，最终公共牌、`winners`、各座位 `net` 全部精确重放（各 0 例外）；173 带 `pot_results` 的摊牌手，其原始 `pot_results` 与当前引擎重放结果**逐项一致**（0 例外）；`showdown_hands` 亦 0 例外。
2. `docs/23` §6.1 标记的「历史 `pot_results` 与当前结算明细不一致」，在本轮口径下**只**能归入**缺项类**：这 4 手（连同 `921463e8`）的原始 `history_json` **根本不含** `pot_results`（也不含 `showdown_hands`），因此**不存在**可与当前结算比较的历史值。四手均可完整重放，其 board / winners / net 与记录**完全一致**。
3. **成因的最强解释（证据支持，非证明）**：这 5 手产生于 `pot_results` / `showdown_hands` 被写入历史 JSON **之前**的旧记录形态；时间边界干净（全部早于 07:36:52，之后无例外）。这属于**历史序列化字段缺项**，**不是**结算规则差异或回归。
   - **残留限制**：`git log -S "pot_results"` 显示该字段序列化由 `8ba93c1`（提交时间 `2026-09-09 16:00:38`）引入，**晚于**观测到的边界 `07:36:52`——即当时运行的进程领先于提交（开发工作树）。写入这 5 手的**确切代码身份**无法仅凭 git 还原；结论只依赖「字段不存在 + 时间边界干净」这一事实，不依赖代码身份。
4. **是否修改结算规则：不需要，本轮也不修改。** 无任何证据指向 `poker/` 结算语义（`_settle_showdown` / `project_pot_layers` / 余数分配）存在错误；5 手的 `net` / `winners` 与重放一致，且其当前结算明细自洽（各池 `shares` 之和等于 `amount`）。
5. **下游影响（只读观察）**：`project_hand_history` 只投影**存在**的键，故这 5 手经 API 投影后不含 `pot_results` / `showdown_hands`；`frontend` 对两者均做了存在性守卫（缺失则整块不渲染），**优雅降级**，不影响其它字段与页面。
