# 14 进行中对局仅驻留内存：热重载导致「下一手」返回 404

> 本文档记录一次本地排查中观察到的现象：后端热重载会清空进行中对局的内存运行态，导致前端操作报「对局不存在或已不在内存中」。
>
> 本文档是**现象记录与待办**，不改变任何既有实现；是否修复留待后续决定。

---

## 1. 现象

在牌桌页点击「下一手」，前端弹出错误：

```
对局不存在或已不在内存中
```

该错误来自 `GET/POST /games/{id}` 的 404 分支（`app/api/games.py`）。此时：

- 数据库中该 `session` 记录仍然存在，`status` 仍为 `active`；
- 但 `GET /games/{id}` 返回 404，该局无法继续，也无法恢复。

---

## 2. 根因

后端把进行中的对局放在**进程内存**里（`app/api/games.py` 的模块级 `_registry: dict[str, GameRuntime]`），只有**已完成**的手牌会落库。模块 docstring 已声明该取舍：「进行中的对局仅驻留内存，重启后需重新创建」。

因此**任何进程重启都会丢失所有进行中的对局**。本地开发的启动命令带 `--reload`：

```bash
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

`--reload` 默认监听**整个工作目录**（`backend/`）下的 `.py` 文件。于是任何一次源码改动（包括新增/修改 `backend/tools/`、`backend/tests/` 下的脚本）都会触发重载，`_registry` 被清空。

### 本次证据链

| 时刻 | 事件 |
|---|---|
| 17:41:25 | 最后一手落库，对局仍在进行 |
| 17:45:08 | 新增 `backend/tools/inspect_hand.py` |
| 17:45:09 | uvicorn 工作进程重启（子进程启动时间），`_registry` 清空 |
| 之后 | 点击「下一手」→ 404 |

对照：uvicorn 父进程启动于 15:55:46，而工作子进程启动于 17:45:09，二者不一致即说明发生过热重载。

---

## 3. 影响

1. **进行中的对局不可恢复**：引擎、底牌、动作线均在内存中，重载后无法续玩，只能重开一局。
2. **前端不持有对局标识**：`session_id` 只存在于 `GameTable` 组件的内存变量里，未写入 `localStorage` 或路由；因此刷新页面同样会丢失当前对局。
3. **残留「僵尸」对局**：无法继续的 `active` 会话仍留在数据库中，会一直出现在 `/games` 列表与历史/统计视图里（本地库中已积累多条 2026-09-09 的 `active` 记录）。

---

## 4. 临时规避

启动后端时把热重载范围限定到 `app` 包，使改动 `tools/`、`tests/` 不再触发重启：

```bash
cd backend && uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 \
  --reload --reload-dir app
```

若希望改测试也触发重载，可再加 `--reload-dir tests`，但**不要**把 `tools` 纳入监听范围。

---

## 5. 后续可选修复（尚未实施）

| 方向 | 说明 | 代价 |
|---|---|---|
| 明确重载范围 | 把带 `--reload-dir` 的启动命令写进 `README.md` 的「快速开始」，减少误触 | 极低，仅文档 |
| 前端持久化对局标识 | `session_id` 存入 `localStorage`，刷新后可尝试恢复；恢复失败时给出明确提示 | 低，仅前端 |
| 错误提示更准确 | 404 时区分「进程重启导致丢失」与「确实不存在」，引导用户重开一局 | 低，需后端提供可判定的信号 |
| 运行态可恢复 | 进行中对局落库或由 `history_json` 重建引擎；重启后可续玩 | 高，需扩展持久化与恢复逻辑，且与当前「只存已完成手牌」的取舍冲突 |
| 清理僵尸对局 | 过滤或标记无法恢复的 `active` 会话 | 低，但需定义「无法恢复」的判定 |
