## 2. 裁定内容

1. **口径**：自本裁定起，包络比对以「整个调用」（即 `uv run python -m …` 这一次调用的进程组）的**最大常驻集**为准；模块自记的 `resources.peak_rss_bytes` 仍**必须照实报告**，但它是**下界**，不再单独作为包络判据；
2. **数值**：包络数值**不变**（`≤1800 s` / `≤1 GiB` / `≤100 MiB`）；用户的「RSS 预算未来允许适当放宽」表态**尚未**落地为任何数值变更，本文件**不据它做任何处置**；
3. **并列报告**：此后每次回执**必须并列**给出「整调用最大常驻集」与「模块自记峰值」，并注明口径；
4. **不追溯**：本裁定**不**追溯改写 v6 / v7 / v8 的任何回执；那些回执中引用的 RSS 值按其形成时的口径有效，但**应被理解为下界**（此理解由 `docs/phase6/70` §7.3 首次披露，本文件确认其为裁定前提）。

## 3. 本轮三个运行在整调用口径下的重新比对

| 运行 | 整调用 `real` | 整调用最大常驻集 | 模块自记 | 与 `≤1 GiB` 的关系 |
|---|---|---|---|---|
| 阶段 `A`（失败轮，族集参量缺陷，`docs/phase6/68`） | `4.51 s` | `192,593,920 B`（`183.67 MiB`） | `73.13 MiB` | **内** |

阶段 `B` 的 **wall 与输出**在该口径下仍在包络内（`503.76 s ≤ 1800 s`；`63.50 MiB ≤ 100 MiB`）；**只有 RSS 一项超出**。

## 4. 已发生的包络超出：事实与处置

1. **事实**：阶段 `B` 的整调用峰值 `1212.63 MiB` 超出 `1 GiB` 包络 `18.4%`。该运行在本文件成文**之前**已经完成（授权文本要求「触及包络则停止并如实报告」，但发现时点晚于运行结束）；
2. **处置**：**停止推进**——不进入补算、不自行扩容、不改任何包络数值；超出事实已在 `docs/phase6/70` §6 与本文件 §3 如实记账；
3. **不得**把该运行说成「包络内通过」，也**不得**说成「包络已被放宽」；其产物（`-v9/runs/stage-b/` 两个文件）**原样保留**，sha 不变；
4. **不得**据本裁定回溯地宣称历史运行是否超包络——历史轮次**未记录**整调用口径的读数，只能标注为**未知**。

## 5. 对未来运行的含义（含补算的风险推演，**是推演不是读数**）

补算路径（`backend/tests/mixed_bot_recheck.py`）与阶段 `B` 的关键差别在于**序列化载荷**：

- 阶段 `B` 的自记值之所以远低于整调用峰值，是因为取样点早于「报告（`18000` 行）× 最多 `3` 轮 + 观测工件（`45,901,341 B`）」的序列化；
- 补算的输出很小（v8 为 `324,904 B`），其**序列化相关**的峰值增量应远小于阶段 `B`；
- ⇒ 在整调用口径下，补算的真实峰值**预计接近其自记值**：v8 自记 `958.73 MiB`（余量 `6.37%`，**未归因**），本轮的补算若同量级，**很可能贴着 `1 GiB` 甚至越过**。

**该推演不是读数**，也不得作为放宽包络或跳过补算的依据；它只说明：**补算的包络处置必须先由用户裁定**，不能默认沿用。
