## 3. 依据（照录要点，不改写原文）

2. **两层固定（`74o` §8.2）**：§8.2.1 为 ②／③ 前的推导输入锁定；§8.2.2 为 ⑥ 的最终运行冻结；二者**不得**混同。`CampaignLockVersions`（`74r`／实现）只承载版本号，**不**表示 ⑥ 第二层冻结（`74t` 已登记）。

## 4. 拟锁定的五类对象（逐类：现状 / 候选 / 推荐 / 待裁定）

本节「现状」= 已裁定设计方向（`74j`／`74k`）＋ 运行器**当前实现口径**（**未锁定**）。候选中的具体规则均**待裁定**。

### 4.1 对象一：配对与重置口径（`pairing_and_reset`）

**白名单归属**：**属于**「配对与重置口径」。**② 使用**（C-1′、`V_max^C` 中 `E`、`d_h` 定义）；**③ 使用**。

**现状（未锁定）**

- 设计方向（`74j` §4、`74k` §4.1）：**D-a** 两臂同一份注入发牌；座位指派相同，仅被测座位上身份不同（臂 m 被测、臂 b 基线）；**O-a** 其余座位均为基线身份；非被测座位随机材料两臂共享（K-2′ 与 `74l`）；每手每臂新建引擎、全员起始 `S`、手内不补码（S-a）；`d_h = m_h − b_h`，`e_h = 100 · d_h / BB`，`m_h`／`b_h` 为被测座位净筹码（含盲注与全部投入）。
- 实现：`DomainRunSpec` 要求显式 `starting_stack`、`schedule`；**不**实现配对运行；`verify_frozen_inputs` 等只校验规格与冻结输入绑定，**不**计算 `d_h`。
- `74h` §8.2：配对口径 `d_h` 曾登记为未定义而阻断进入 ③；第一层锁定须把「同一 deal」「两臂标识」「重置」写为可执行判据。

**候选**

| 编号 | 候选内容 |
|---|---|
| P-1 | 锁定 **D-a** 为唯一允许的「同一 deal」口径：发牌材料 `G_h` 两臂逐字节相同、由 L-1 映射确定底牌与公共牌 |
| P-2 | 锁定 **O-a** 与其余座位材料共享规则（与 K-2′ 索引一致，不重复发明索引） |
| P-3 | 锁定每手重置：每手每臂独立引擎实例、开手时全员筹码恰为 `S`、手内不得补码或跨手结转 |
| P-4 | 锁定 `d_h`／`e_h` 符号定义与臂 m／臂 b 的对应关系（被测座位为 `probed_seat`） |
| P-5 | 允许 **D-b**（双洗牌种子）作为备选——须单独论证与 L-1 注入路径一致，**不推荐**（`74j`） |

**推荐项**：`P-1`＋`P-2`＋`P-3`＋`P-4`。理由：与 T-a、K-2′、S-a 及已锁定 L-1 一致；不把「同一 deal」寄托在洗牌消耗顺序上。

**待裁定项**：是否在锁定文本中写死「无抽水、筹码守恒」为 C-1′ 前提子句；`m_h`／`b_h` 是否包含边池分配后的整数筹码（与 §4.2 联动）；版本号 `pairing_and_reset` 的首个锁定版本是否取 `1`。

**可执行判据候选**：给定冻结口径与一手规格，能否在不读策略输出的前提下判定两臂发牌材料一致、重置前后筹码向量符合 `S`、且 `d_h` 可由规则从引擎终态筹码减 `S` 得到（③ 机械核验时仍不得读身份输出——只核验规则与引擎结构是否支持该计算路径）。

### 4.2 对象二：每手上界规则（`per_hand_bound`）

**白名单归属**：**属于**「引擎规则给出的每手上界」。**② 使用**；**③ 使用**（形式／机械／前提）。

**现状（未锁定）**

- `74j` §4.3：在全员 `S`、无抽水、守恒、手内不补码前提下，`d_h ∈ [−N·S, N·S]`，`D := N·S`，`E := 100 · N · S / BB`；与 `73b` 的 `2(N−1)S` 关系已登记（`N ≥ 3` 时 `N·S` 更紧）。
- `74o`：只锁**规则式**，不代入具体 `N`、`S` 数值。
- 实现：人数 `2 ≤ N ≤ 23` 已在校验层强制（L-1／G-1）；**未**在包内证明 `|d_h| ≤ N·S`（无可执行路径）。

**候选**

| 编号 | 候选内容 |
|---|---|
| B-1 | 锁定上界为 `D := N · S`（与 `74j` 推荐一致） |
| B-2 | 锁定上界为 `D := 2(N−1)S`（历史 `73b` 口径，更松） |
| B-3 | 锁定规则推导前提集合（无抽水、守恒、手内不补码、整数筹码单位）及边池／平分／余筹不越界的**机械核验义务**（③，不读身份输出） |
| B-4 | 把 `E` 与 `BB` 的关系写进锁定文本（`E = 100 · D / BB`），并规定 `BB > 0` 由运行前规格保证 |

**推荐项**：`B-1`＋`B-3`＋`B-4`。理由：与 `74h` 域 C 上界记号一致；边池情形须在 ③ 按规则核验而非假设。

**待裁定项**：是否在锁定文本中明确「上界对整数筹码单位逐手成立」；是否与 `poker/` 规则变更联动（变更须新后缀并失效 ③）；`per_hand_bound` 版本首值是否取 `1`。

**可执行判据候选**：对冻结规则，任意满足前提的手局，理论极值 `±N·S` 可达性是否需要在 ③ 用构造性手局说明（只读规则引擎，不读身份输出）。

### 4.3 对象三：片段划分与 `K_min` 模板（`fragment_template`）

**白名单归属**：**属于**「块模板、片段划分」。**② 使用**（F-0、`V_max^C = E²/K_min`）；**③ 使用**。

**现状（未锁定）**

- F-0（`74j` §8.2、`74k`）：块内手集合划分为**不相交**片段；每片段手数 `K_f`；`K_min := min_f K_f`；`K_min ≥ 2` 时 `V_max^C/M_C² < 1`（`74h` §3.5）。
- 实现：`schedule` 为块内手序计划，**无**片段字段；片段逻辑不在 `verification/` 内。

**候选**

| 编号 | 候选内容 |
|---|---|
| F-1 | 锁定片段划分为块内手序 `hand_ordinal` 上的不相交区间划分（显式列表或模板函数） |
| F-2 | 锁定 `K_f` 为片段内手数，且 `Σ_f K_f = H`（块内总手数） |
| F-3 | 锁定 `K_min ≥ 2` 为采用 `V_max^C` 非退化上界的**必要条件**；`K_min = 1` 时须登记退化 |
| F-4 | 片段模板是否允许随 `block` 变化（跨块同一模板 vs 每块独立模板） |
| F-5 | 片段是否必须与 `schedule` 中实际手序一一对应（禁止空洞手序） |

**推荐项**：`F-1`＋`F-2`＋`F-3`＋`F-5`；`F-4` 推荐「块内常量模板、跨块可重复同一规则但手序独立生成」（与 K-3 逐手独立一致）。

**待裁定项**：模板由谁供给（仅文档冻结 vs 将来写入 `DomainRunSpec` 新字段——若需改规格须单列实现授权，**本提案不授权改代码**）；`fragment_template` 版本首值是否取 `1`。

**可执行判据候选**：给定块内 `H` 与划分，可机械检查不相交、完备、`K_f` 为正整数、`K_min` 可算。

### 4.4 对象四：适用权重类（`weight_class`）

**白名单归属**：**属于**「块内权重」。**② 使用**（`74f` §4.2.3 适用权重类）；**③ 使用**。

**现状（未锁定）**

- 域 C：`74j` §8.3 推荐 `w_f := K_f / Σ K_f`（按手数加权）；`74h` §3.5 对**一切**非负且和为 1 的片段权重给出 `V_max^C`。
- 域 A／B：层权重 `v_ℓ` 候选 W-b（按 `M_ℓ` 比例）等在 `74j` §8.3；层定义本身不在本文件范围，但权重**类**须先锁定。
- 实现：无权重字段；**不**计算 `Σ w_f²/K_f`。

**候选**

| 编号 | 候选内容 |
|---|---|
| W-1 | 域 C：锁定「片段权重向量 `w` 满足 `w_f ≥ 0`、`Σ_f w_f = 1`」为适用类；是否进一步锁定唯一推荐 `w_f ∝ K_f` |
| W-2 | 域 C：锁定默认估计对象为按 `w_f ∝ K_f` 的块内加权平均（与 `74j` 推荐一致） |
| W-3 | 域 A／B：锁定层权重类为「非负且和为 1 的有限维向量」，并推荐 W-b 为默认写法 |
| W-4 | 明确具体数值权重属 ⑥ 第二层冻结，第一层只锁**类**与可选默认公式 |
| W-5 | 禁止在 ② 使用未锁定类外的权重（事后变更须新编号并失效 ②／③） |

**推荐项**：`W-1`＋`W-2`＋`W-4`＋`W-5`；域 A／B 的 `W-3` 作为**待裁定**是否并入同一锁定文本或另开对象（避免与域 C 片段权重混淆）。

**可执行判据候选**：给定 `K_f` 与候选 `w`，可检查非负、归一、是否落在锁定类内。

### 4.5 对象五：庄位与轮换规则（`seat_rotation`）

**白名单归属**：**属于**「座位轮换」。**② 使用**为**条件性**（`74o`：仅当未来 ② 推导实际引用时；既有 `74h` `V_max^C` 推导**未使用**本对象）。**③ 使用**为「是」（`g_h` 中手序确定量的核验）；锁定时点仍为未来 ② 或 ③ **首次实际引用**前，以先到者为准。

**现状（未锁定）**

- `74j` §4.1：被测座位相对庄位按块内手序**确定性轮换**为设计方向；轮换规则冻结属域规格。**不**等于 `74h` 已生效的域 C 上界式已引用该规则。
- 实现：`HandPlan` 含 `hand_ordinal`、`button`、`probed_seat`；校验与 `num_players` 的范围关系在规格层；**无**从手序推导庄位／被测座的函数。

**候选**

| 编号 | 候选内容 |
|---|---|
| R-1 | 锁定「庄位 `button` 为 `0 … N−1` 内整数」及与 `hand_ordinal` 的确定函数关系（例如固定递增轮换公式，须写死） |
| R-2 | 锁定「被测座位 `probed_seat` 为确定函数 `(button, hand_ordinal, N)`」且与 `74n` §4.3 的 `bot_seats = (被测座位,)` 一致 |
| R-3 | 锁定其余座位身份安排仅由 O-a 与座位号决定（不在此对象重复 K-1） |
| R-4 | 保持「调用方显式供给 `HandPlan`」，锁定文本只规定**合法计划**须满足的轮换恒等式（实现继续不推断） |
| R-5 | 允许运行器将来根据锁定规则生成 `schedule`（须另案实现授权，**本提案不推荐**） |

**推荐项**：`R-1`＋`R-2`＋`R-4`（先锁数学关系与可执行判据，不强制运行器自动生成）。理由：与当前 `74t` 包边界一致；避免在锁定阶段偷偷引入可执行路径。

**待裁定项**：具体轮换公式（例如 `button = (h−1) mod N`、`probed_seat = (button + f(h)) mod N` 的 `f`）；是否要求 `schedule` 严格按 `hand_ordinal` 递增；`seat_rotation` 版本首值是否取 `1`。

**可执行判据候选**：给定 `N` 与 `schedule`，可机械验证每条手计划满足锁定恒等式与座位范围。
