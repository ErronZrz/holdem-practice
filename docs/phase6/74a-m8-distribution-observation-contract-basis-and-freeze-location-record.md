## 3. 裁定一：依据地位

1. `73b` §5.6 及其 §11.1 第 `28` 项，在本战役内是**未冻结的设计来源（草案文本）**，**不具冻结效力**。
2. `74` 不得把该契约表述为：已生效的契约要求、已获批准的实现依据、已完成的前置条件、已实现或已变化的接口。
3. 该契约所载的 8 条要求（与采样同源、查询不改变随机流、输入口径、`HandMode` 唯一口径与权重一致性、金额语义与概率单位、缺失即不可判定、接口影响说明、次序），在本战役内只作为**候选要求集**；须由 `74` 内的契约冻结文档**逐条**确认、修订或替换后，才成为实施依据。
4. 其中已由用户单独裁定的理论权重（`w_NORMAL = 0.80`、`w_CAUTIOUS = 0.10`、`w_PRESSED = 0.10`）保持原值不变；但连同其所属规格一并，**不因本记录获得冻结效力**。

## 4. 裁定二：承接来源

1. 该契约由 **`74` 族**承接；`73` 族不承接、不续写。
2. `73b` §5.6 第 `8` 条写死的次序中，第 (1) 步为「`73` 冻结本节的契约要求」。该步骤**已无法在 `73` 内执行**：`73` 已由 `73f` 关闭，不得续号，也不得新增或修改 `73` 族。
3. 因此，该步骤的功能由 `74` 内的一次契约冻结承接；原次序的其余部分保持不变并继续适用，顺序不得颠倒：

```text
(1) 在 74 内冻结契约要求          ← 替换原第 (1) 步的“在 73 内冻结”
(2) 74 实现并测试该契约
(3) 契约未实现或验证未通过 ⇒ 域 A / 域 B 记「不可判定」
(4) 只有前三步完成后，才允许冻结新身份清单并运行验证
```

4. 本记录**不**完成第 (1) 步：契约要求尚未在 `74` 内冻结。因此当前状态下，第 (3) 步的「不可判定」结论仍然成立。

## 5. 裁定三：规格冻结位置

1. 契约规格的冻结位置在 **`74` 族**，由该族后续的一份**专门文档**承担。
2. 该冻结文档的**编号在创建时按追加顺序确定**；本记录**不预占编号**。
   - 该纪律有既有先例：`73b` §11.3 已记录，`73a` §10 曾把「新身份改造规格」预先登记为 `73c`，该编号设想随后**作废**并改由 `74` 承担。本记录不重复这种预占。
3. 冻结文档至少须包含：`73b` §5.6 全部 8 条的**逐条处置**（确认 / 修订 / 替换，并注明来源）、金额语义与概率单位的冻结写法、缺失与失败的处置、以及接口形态。
4. 在该冻结文档落盘之前，本契约**不得被实现**，也**不得被当作实现依据**。
