## 4. 设计点一：被测座位两臂材料 `Q_h^m` / `Q_h^b`

### 4.1 候选

| 候选 | 内容 | 影响 |
|---|---|---|
| **T-a 独立抽取** | `Q_h^m` 与 `Q_h^b` 按不同用途标签分别从外部随机化协议取得，互不共享 | 实现最简；两臂身份不同，格式可各自定义；不涉及「共享」的含义 |
| T-b 共享原始材料 | 两者取同一份按 `(campaign configuration, block, h, 被测座位)` 查表的原始材料，再经各身份各自的固定格式映射 | 两臂身份不同、随机结构不同，「同一原始材料」不对应任何可解释的公共随机量；紧度收益无依据 |

两者均**不**影响 C-2′（C-2′ 只要求不同手独立），也均**不**主张逐决策一致。

### 4.2 推荐

**T-a**。理由：被测身份与 `heuristic@1` 的随机结构不同（G1、G3 与 `74l` §5.2），共享原始材料没有可解释的配对含义，却会增加「共享」口径的定义负担。若未来被测身份与基线属同一随机结构族，可另行申请 T-b。

## 5. 设计点二：随机化协议预注册规格骨架（只定结构，不生成材料）

按 `74k` §3.2 第 3 条写出五项结构：

### 5.1 来源接口与环境范围

- 唯一来源接口：由预注册指定的**单一**外部随机源调用接口（候选：操作系统密码学随机字节接口）；本文件**不**冻结具体接口。
- 环境范围：执行生成的主机、操作系统与解释器版本须记录；生成只在一次预注册的生成步骤中进行，与任何对局运行分离。

### 5.2 用途标签、索引与有限输出域（推荐结构）

| 用途标签 | 索引 | 有限输出域 | 说明 |
|---|---|---|---|
| `deal` | `(config, block, h, k)`，`k = 0 … 2N+4` | `{0, …, 52 − k − 1}` | 部分 Fisher–Yates 的第 `k` 步；共 `2N + 5` 个 |
| `opp` | `(config, block, h, s)`，`s` 为非被测座位 | `heuristic@1` 种子域 `{0, …, 2^64 − 1}` | K-2′ 的每手每座位初始材料，两臂共享 |
| `arm_m` | `(config, block, h)` | 由被测身份的输入映射定义（§6.2） | T-a 下臂 m 被测座位 |
| `arm_b` | `(config, block, h)` | `{0, …, 2^64 − 1}` | T-a 下臂 b 被测座位（`heuristic@1`） |

- 种子域取**非负**有限整数集合；`2^64` 为推荐候选，冻结在 ⑥。
- 索引只用于查表（`74l` §5.4 第 5 条），**不得**作为派生输入。

### 5.3 无偏拒绝采样与继续规则

- 对输出域 `{0, …, n − 1}`：每次读取 `b` 位原始值 `r`（`b` 为不小于 `⌈log₂ n⌉` 的 `8` 的倍数，按用途冻结）；若 `r < n · ⌊2^b / n⌋` 则输出 `r mod n`，否则**丢弃并按同一规则继续读取下一段原始值**，不得改换用途、不得截断为有偏值。
- 每次读取（无论接受或拒绝）都须按 §5.5 的逐读取审计材料记录，不得只记汇总计数。

### 5.4 一次性生成与完整落盘

- 全部用途、全部索引在**一次**生成步骤中按冻结的遍历顺序生成；生成结果完整写入清单文件并计算摘要。
- **禁止**：重试、替换、部分重生成、按任何结果（含机械量）筛选；生成失败只能使本次冻结尝试终止。

### 5.5 可审计记录

**汇总层**至少包含：来源接口标识、环境信息、生成起止时间、遍历顺序规范、每个用途的条目数、拒绝次数、清单文件摘要、生成程序的代码摘要。

**逐读取层**（使拒绝采样过程可机械复核）：

- **原始字节转录**：按实际读取顺序，把从来源接口取得的**全部**原始字节（含被拒绝的部分）完整、连续地写入转录文件；转录文件的摘要写入汇总层。
- **逐读取记录**：对每次读取按顺序记录——全局读取序号、用途标签、索引、位宽 `b`、该段原始值 `r` 在转录中的起止偏移、接受 / 拒绝标记、接受时的输出值。
- **不可变顺序承诺**：转录文件与逐读取记录在生成步骤结束时一次性计算摘要，并与清单文件摘要一同写入汇总层；此后任何改动都会使摘要不符。承诺的具体形式（例如摘要链或一次性封存）在预注册时冻结。
- **可复核性**：核验方仅凭转录文件、逐读取记录与冻结的遍历顺序 / 位宽 / 拒绝规则，即可逐条重算每个用途、每个索引的输出值与拒绝判定，并检查转录无缺口、无重叠、无多余字节。

上述材料只服务于**协议执行核验**（发现隐藏替换、重试或选择性保留等违例），**不**证明来源的真实独立性或均匀性。

**核验能力边界**（照录 `74k` §3.2 第 4 条）：只能检查来源、调用顺序、完整性、无重复生成与映射规则；**不能**证明实际独立性或均匀性。

## 6. 设计点三：材料到各身份构造参数的固定映射

### 6.1 发牌材料 `G_h`（两臂共享）

- 由 `deal` 用途的 `2N + 5` 个均匀整数执行部分 Fisher–Yates，得到 `52` 张牌规范序中的前 `2N + 5` 张。
- 固定分配规则（推荐）：第 `2s` 与 `2s + 1` 张为座位 `s` 的两张底牌（`s = 0 … N−1`），其后 `5` 张依序为翻牌 `3` 张、转牌、河牌；经引擎的注入开手路径传入（`74j` §3 F2）。
- 该映射为确定函数；牌的规范序须冻结。

### 6.2 被测身份（臂 m 被测座位）

被测身份在本战役中尚未创建；其输入映射须随被测身份一并冻结。以现有混合策略族的接口为参照，推荐结构：

- **主键注入**：`arm_m` 的原始材料为 `32` 字节均匀值，直接作为主键注入。实现依据是混合策略构造器的 `root_key` 分支——传入时直接使用、不执行 `seed → 主键` 派生（G9）；`api/games.py` 第 82–83 行只是「向策略注入**已由请求 seed 派生**的主键」的旁证，**不**是外部原始字节直接输入的完整证据。手内由主键派生的座位键 / 模式 / 行动随机量属于 `g_h` 的一部分，只影响**同一手内**，不涉及跨手独立性。
- **主键硬校验与禁止项（运行器设计要求，须在实现 / 测试阶段强制）**：
  - 注入值必须是类型为 `bytes`、长度**恰好** `32` 的对象；类型或长度不符即硬失败（现有构造器不作此校验，G9，故由运行器承担）；
  - 运行器中**禁止**调用 `seed → 主键` 的派生函数替代 `arm_m` 材料，也禁止以任何其他方式改写该材料；
  - 纳入执行身份（§7.4）的固定项：被测身份的规范标识；HMAC 算法（当前为 HMAC-SHA256）；派生消息编码（当前为紧凑 JSON、ASCII 转义）；派生标签（当前为身份标识与 `bots`、`seat`、`hand`、`mode`、`action`）；按身份标识取用的规则口径版本。
- **手号字段**：输入契约要求正整数手号（G2）。推荐取**块内手序 `h`（从 `1` 起）**，仅作可追溯标识；因每手主键独立，手号取值不影响 C-2′。
- **Bot 座位集合与风格（须裁定）**：混合策略按已绑定 Bot 座位的升序序号分配风格，Bot 座位集合取自公开摘要的 `bot_seats` 字段，构造器没有显式风格参数（G3、G8）。
  - **现有实现可表达的候选**（由运行器为摘要跟踪器设定 `bot_seats`，不改 `strategy/**`）：
    - **B-1**：`bot_seats` 只含被测座位 ⇒ 被测座位恒为 `TIGHT`；
    - **B-2**：`bot_seats` 为全部座位 ⇒ 被测座位的风格为其座位号在全部座位升序中的序号对应的风格，随被测座位的轮换而变化。
  - **B-3**（由被测身份的规格显式写定风格分配）**仅适用于未来另行创建并冻结的被测身份**：现有混合策略族没有该能力，实现 B-3 需要新版本化的被测身份、策略接口扩展或明确的替代构造路径，均涉及 `strategy/**` 改动与身份创建，须另行授权；B-3 **不构成**现有混合策略族的运行器选项，也**不**在本文件 §7.2 的运行器边界内。
  - **推荐（仅针对现有实现）**：**B-1**。理由：被测身份的风格在全部手中固定，不随被测座位轮换而改变，避免把「座位号」与「风格」混杂进配对差；代价是只覆盖该身份的 `TIGHT` 风格，此限定须在估计对象中如实写明。B-2 作为备选。本项与 K-4 实例化口径直接相关，`bot_seats` 的取值规则须纳入执行身份。
- **公开摘要**：每手每臂新建摘要跟踪器，按 G2 的方式初始化与增量消费；输入状态按「先脱敏投影、再附摘要」构造。

### 6.3 `heuristic@1`（臂 b 被测座位与全部非被测座位）

- 经受控注册表构造，传入**非空**整数 `seed`（`74l` §6 第 3 项），取自 `opp` 或 `arm_b` 用途的材料；
- `samples`、`bluff_freq` 取类默认值（G5），其有效值与来源绑定纳入执行身份范围（§7）；
- 输入状态为脱敏投影（与应用路径一致）。

## 7. 设计点四：运行器与 K-4 执行身份覆盖清单

### 7.1 运行器目录候选

|---|---|---|
| **V-1** | 新建 `backend/app/verification/`（纯 Python，依赖 `poker/` 与 `strategy/`，不依赖 `api/` / `llm/` / `storage/`） | **推荐**：与 `analysis/`（复盘与错误检测）职责分离；位于后端包内便于复用受控注册表 |

### 7.2 实现边界（推荐）

- 每手每臂：新建引擎（全员 `S`）→ 注入开手（庄位、底牌、公共牌来自 `G_h` 与冻结的庄位规则）→ 每座位新建策略实例并注入该手材料 → 按引擎合法动作推进至本手结束 → 读取被测座位净筹码（G4）；
- **注入前硬失败校验**（运行器承担，因注入开手路径本身不校验，G10）：在调用注入路径之前逐项检查，任一不满足即本手硬失败并终止本次运行，**不得**回退到随机开手路径，也不得修补或重取材料：
  1. 底牌映射的座位集合**恰为** `{0, …, N−1}`，无缺失、无多余；
  2. 每个座位**恰好** `2` 张底牌；
  3. 公共牌**恰好** `5` 张；
  4. 总牌数恰为 `2N + 5`，且**全局无重复**（含底牌之间、公共牌之间、底牌与公共牌之间）；
  5. 每个元素都是引擎的牌类型对象，且属于冻结的 `52` 张规范牌集合；
  6. 庄位为整数且落在 `[0, N−1]`；
  7. 两臂注入的发牌材料逐项相同（同一 `G_h`）。
- 两臂除被测座位身份与其材料外完全相同；
- 运行器**不**修改 `poker/**` 与 `strategy/**`（因此 §6.2 的 B-3 不在本边界内）；**不**读写数据库；**不**调用 `api/` 或 `llm/`；
- 输出只含逐手 `m_h`、`b_h`（及定位字段）与运行元数据；不输出策略内部量。

### 7.3 执行环境

与既有包络一致：单进程、无并行；包络数值（`wall ≤ 1_800 s`、整调用最大 RSS `≤ 1.5 GiB`、输出 `≤ 100 MiB`）**不**在本文件改变，其可行性处理属 ⑤。
