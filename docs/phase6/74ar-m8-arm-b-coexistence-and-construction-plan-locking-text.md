## 7. 构造计划载荷的提案形状

两套载荷是两个摘要对象。版本 1 的字节形状保持 `74r` §8.3.9，本提案不往里面加字段。版本 2 使用另一套形状。因此同一批整数不会因为套错形状而得到同一个 `construction-plan-digest`。

本提案不计算任何一个摘要，也不写下任何一条实际键或实际 seed。尖括号是形状里的占位，不是取值。

### 7.1 版本 1

协议 schema 为 `randomization-protocol-v1` 时，载荷仍是 `74r` §8.3.9 的 JSON 数组：每手每臂一项，`seats` 按座位号升序，每座恰一项，该项含单个字段 `material`。`arm_b` 与 `non_probed` 都是每座一条。没有 κ 列表，也没有「κ 缺席」这种哨兵字符串。

版本 1 的缺席取值就是这套形状本身：座位项里有 `material`，没有 `materials`。不得用一条空的版本 2 列表冒充版本 1。

### 7.2 版本 2

协议 schema 为 `randomization-protocol-v2` 时，载荷是下面这个对象，而不是 §7.1 的数组：

```json
{
  "schema": "construction-plan-v2",
  "hands": [
    {
      "hand_ordinal": "<positive-int>",
      "button": "<non-negative-int>",
      "probed_seat": "<non-negative-int>",
      "arm": "<under-test | baseline>",
      "summary_seats": ["<int>"],
      "summary_scope": ["<int>"],
      "probed_seat_style": "<tight | null>",
      "seats": [
        {
          "seat": "<non-negative-int>",
          "role": "<non-probed | probed-under-test | probed-baseline>",
          "identifier": "<heuristic@1 | mixed-local@9>",
          "interface": "<registry-seed | material-key>",
          "requires_public_summary": "<false | true>",
          "seat_scope": "<null | probed-seat-only>",
          "materials": [
            {
              "purpose_label": "<arm_m | arm_b | non_probed>",
              "index_key": ["<...>"],
              "value": "<non-negative-int>"
            }
          ]
        }
      ]
    }
  ]
}
```

对象顶上的 `schema` 只出现在这套版本 2 载荷里。`74r` 的 Q-6 确认的是当时那两个载荷不增加 `schema`：入口代码载荷（§8.3.8）和版本 1 的构造计划数组（§8.3.9）。本提案不改那两个载荷，版本 1 数组仍然没有 `schema`。版本 2 另成一个对象并写上 `construction-plan-v2`，是为了让两种形状在摘要上不能互换：把版本 2 对象交给版本 1 的重算，或把版本 1 数组交给版本 2 的重算，都对不上。这不把 Q-6 读成「以后任何载荷都不得出现 `schema`」。

手与臂的次序、座位号升序、两侧角色和接口，与 `74r` §8.3.9 相同。变的是材料字段：版本 2 的座位项只有 `materials` 数组，没有单个 `material`。

`materials` 不是该臂在对局里实际走到的决策，也不是分叉之后新出现的公开投影。它是闭合集上的完整切片，再配上已提交材料里同一键的整数。规格、闭合集和材料三者足以重算，不读取对局过程。

| 座位 | 切片 |
|---|---|
| 被测臂的被测座位 | 闭合集里该 `hand` 的全部 `arm_m`。版本 2 的这条键没有 `seat`，所以切片位置是 `(hand, 用途)`，长度恰为 1，键仍是 `(campaign, block, hand)` |
| 基线臂的被测座位 | 闭合集在该 `(hand, seat, arm_b)` 上的全部键。`seat` 必须是该手被测座位。长度至少为 1，每条都是六字段 κ |
| 两臂的非被测座位 | 闭合集在该 `(hand, seat, non_probed)` 上的全部键。长度至少为 1，每条都是六字段 κ |

两臂的非被测座位取同一切片：同一组键、同一个整数。共享规则是 `74am` §7，即同一完整 κ 一条整数、两臂同键同值。版本 2 不按 `74r` §8.3.9 所引的 K-2′ 来解释这组切片。被测座位不共享：基线臂只取 `arm_b` 切片，被测臂只取 `arm_m` 切片。

切片必须恰好等于闭合集在该位置上的键，不少也不多。每一项的 `value` 是已提交材料里同一键的整数。对得上的键缺材料，或材料里多出切片没有的键，重算失败。

分叉之后若要消耗切片以外的键，即为协议失败：停止，不补读、不补键。这与 `74ao` 的缺键硬失败相同。编排器是否真能覆盖两臂各自的投影，留在 K-4 复审核对。本提案不把「已经覆盖」写成事实。

当前实现仍要求每手恰好一条 `arm_b`。那不是本提案的粒度。提案允许同一手有多条 κ，条数等于闭合集在该切片上的条数。将来的实现授权不得把「每手恰好一条」写成这套载荷的规则。

### 7.3 逐 κ 项的排序、字段和整数范围

同一座位内的 κ 数组按 `event_index` 的**整数值**升序，不按 `index_key` 里的字符串字典序。因此 `"2"` 在 `"10"` 之前。整数的解析与键上其他整数字段相同：无前导零的十进制，`0` 写作 `"0"`。平局时再按 `sigma_public` 的字符串升序。`74am` 规定同一 `(seat, event_index)` 至多一条 `sigma_public`，所以在已经合法的闭合集上，这条字符串次序不会改变顺序。它仍写在规则里，避免两个不同投影共用一个序号时排序没有定义。`campaign`、`block`、`hand`、`seat` 在该座位内已经相同，不另排。`arm_m` 那一条只有一个元素，不再排序。

每一项只有三个字段：

| 字段 | 规则 |
|---|---|
| `purpose_label` | `arm_b` 或 `non_probed`。`arm_m` 只用在被测臂被测座位的那一条上 |
| `index_key` | 字符串数组，次序与该用途的键字段次序相同 |
| `value` | JSON 整数，满足 `0 ≤ value < 2^256`。布尔、空值、非整数失败。基线 seed 不得为空 |

`samples` 与 `bluff_freq` 不是这三项的字段。`KappaDecisionPlan` 可以继续在内存里描述一次决策，但摘要只覆盖上表这三个字段，不把该结构的类默认值再抄进载荷。

## 8. 与 `construction-plan-digest` 的绑定

条目名不变，仍是 `construction-plan-digest`。不新增身份条目。

重算规则：

- schema 为版本 1 时，对 §7.1 的数组取 SHA-256。
- schema 为版本 2 时，对 §7.2 的对象取 SHA-256。
- 编码仍是紧凑 JSON、键排序、`ensure_ascii = true`、UTF-8、小写十六进制。本提案不产出任何一个十六进制。

版本 1 的身份若带上 §7.2 的对象，或版本 2 的身份若带上 §7.1 的数组，摘要比对失败。版本 1 没有单独的「κ 缺席」摘要；缺席就是 §7.1 那种不含 `materials` 的形状。

§5 写「本提案本身不执行这次替换」。这里仍指不改代码、不改当前身份里的字符串。替换值成为固定值的时点只在 §10：全文审查通过之后。通过之前，表中第一行仍是唯一合法取值。

## 9. 版本 2 的 `supplied-materials-digest`

### 9.1 对审查指示的处理

审查指示是：沿用 `74r` §8.3.10，只换键形；手内按用途遍历顺序，再按完整键升序；`event_index` 按整数值比较。起草方按这一指示写定。版本 2 仍是 JSON 数组，每手一项，每项仍是 `hand_ordinal` 与 `entries`；每条材料仍是 `purpose_label`、`index_key`、`value`。不加 `schema`。这与 `74r` 对 Q-14 的确认相同。

条数不能把版本 1 的「每手恰 `3N + 6` 条、`arm_b` 恰一条、`non_probed` 每座一条」原样套到版本 2。§7.2 已经写明同一手的 κ 可以有多条，条数等于闭合集在该切片上的条数。若送交材料仍强制 `3N + 6`，多出来的 κ 没有位置，独立 ③ 也无法同时满足 §7.2。因此键形按用途更换，`deal` 与 `arm_m` 的条数仍与版本 1 相同，`non_probed` 与 `arm_b` 的条数改为该手闭合集上的对应切片。代价是：版本 2 夹具不能再断言 `3N + 6`，也不能再断言 `arm_b` 恰一条。数组、字段名和不加 `schema` 没有另起一套。

版本 2 构造计划对象上的 `schema` 仍只存在于 §7.2。送交材料不加 `schema`，是因为本载荷沿用 Q-14，两种协议用键形区分，不因为把 Q-6 读成「以后任何载荷都不得出现 `schema`」。§7.2 对 Q-6 的那句仍然有效。

本文件不改 `74r` §8.3.10。版本 1 的送交材料仍只按那一节重算。

### 9.2 载荷

协议 schema 为 `randomization-protocol-v2` 时，对下面的数组取 SHA-256，编码与 §8 相同：紧凑 JSON、键排序、`ensure_ascii = true`、UTF-8、小写十六进制。本文件不产出任何一个十六进制。尖括号是占位，不是取值。下例每种用途只画一条，用来标明键长；`non_probed` 与 `arm_b` 的实际条数由 §9.4 决定。

```json
[
  {
    "hand_ordinal": "<positive-int>",
    "entries": [
      {
        "purpose_label": "deal",
        "index_key": ["<campaign>", "<block>", "<hand>", "<draw>"],
        "value": "<non-negative-int>"
      },
      {
        "purpose_label": "non_probed",
        "index_key": ["<campaign>", "<block>", "<hand>", "<seat>", "<event_index>", "<sigma_public>"],
        "value": "<non-negative-int>"
      },
      {
        "purpose_label": "arm_m",
        "index_key": ["<campaign>", "<block>", "<hand>"],
        "value": "<non-negative-int>"
      },
      {
        "purpose_label": "arm_b",
        "index_key": ["<campaign>", "<block>", "<hand>", "<seat>", "<event_index>", "<sigma_public>"],
        "value": "<non-negative-int>"
      }
    ]
  }
]
```

| 用途 | `index_key` 字段次序 | 键长 |
|---|---|---|
| `deal` | `campaign`、`block`、`hand`、`draw` | 4。与 `74r` §6.2 相同 |
| `non_probed` | `campaign`、`block`、`hand`、`seat`、`event_index`、`sigma_public` | 6。与 `74am` §6.1 相同 |
| `arm_m` | `campaign`、`block`、`hand` | 3。与 `74r` §6.2 相同 |
| `arm_b` | `campaign`、`block`、`hand`、`seat`、`event_index`、`sigma_public` | 6。与 `74am` §6.1 相同 |

键长不符、字段次序不符、或把版本 1 的手级 `arm_b` 键、四字段 `non_probed` 键放进版本 2 载荷，重算失败。版本 1 身份若带上六字段 `arm_b` 或六字段 `non_probed`，按 `74r` §8.3.10 重算失败。两种身份不得互换载荷。

每条键的 `campaign` 必须满足 `74am` §6.6：等于 `randomization_protocol = 2` 的配置摘要。版本号为 `1` 的摘要不得出现在版本 2 材料键上。本文件不生成该摘要。

### 9.3 排序

外层数组按 `hand_ordinal` 严格递增，且与 `schedule-v1` 的 `hands` 逐手一一对应。每手的 `hand_ordinal` 必须等于该手每一条索引键里的 `hand`（`74r` 的 K-3）。

同一手里的 `entries` 先按用途次序 `deal`、`non_probed`、`arm_m`、`arm_b` 排列。这与 `74r` §6.4 和 `74am` §9 的用途次序相同。

同一用途内再按完整 `index_key` 升序，逐字段比较：

| 字段 | 比较 |
|---|---|
| `campaign` | 字符串升序 |
| `block`、`hand`、`draw`、`seat`、`event_index` | 无前导零的十进制，按**整数值**升序。`0` 写作 `"0"`。因此 `"2"` 在 `"10"` 之前 |
| `sigma_public` | 字符串升序。编码规则仍是 `74am` §6.4 |

带前导零、正负号、空白或非十进制的整数字段不是合法键，重算失败。同一用途、同一完整键出现两次，重算失败，不当作平局。

`74am` §6.3 规定同一用途、同一 `(campaign, block, hand, seat, event_index)` 至多一条 `sigma_public`。在已经合法的闭合集上，`sigma_public` 的字符串次序不改变顺序。它仍写在规则里，避免两个不同投影共用一个序号时排序没有定义。共用序号的键集本身仍然非法。

一手内部的 `campaign`、`block`、`hand` 已经相同，不改变该手内部的相对次序。比较仍从完整键的第一个字段做起。

### 9.4 条数与切片

| 用途 | 版本 2 的条数 |
|---|---|
| `deal` | 恰为 `2N + 5`。`draw` 从 `0` 到 `2N + 4`，一步不缺 |
| `arm_m` | 恰为 1。键是 `(campaign, block, hand)` |
| `non_probed` | 恰为闭合集在该手上、该用途上的全部键。座位集合恰为 `{0…N−1}` 去掉该手被测座位。每个这样的座位至少一条，每条都是六字段 κ |
| `arm_b` | 恰为闭合集在该手被测座位、该用途上的全部键。`seat` 必须等于该手被测座位。至少一条，每条都是六字段 κ。其他座位不得出现 |

四项相加就是该手的 `entries` 条数。这个和在每座、每条 `arm_b` 都恰为 1 时才等于版本 1 的 `3N + 6`。版本 2 不把 `3N + 6` 写成规则。

该手 `entries` 里的键集合必须与闭合集里该手的键集合相等，不少也不多。每一条的 `value` 是已提交材料里同一键的整数。对得上的键缺材料，或材料里多出该手切片没有的键，重算失败。分叉之后要消耗切片以外的键，即为协议失败：停止，不补读、不补键。这与 §7.2 和 `74ao` 的缺键硬失败相同。

`deal` 的 `value` 仍按 `74r` 的收缩域检查，本文件不改发牌值域。`arm_m`、`arm_b`、`non_probed` 的 `value` 仍是 `[0, 2^256)` 内的 JSON 整数。布尔、空值、非整数失败。`arm_b` 与 `non_probed` 的基线 seed 不得为空。上界不放宽，多条 κ 也不合成一个上界。

### 9.5 与构造计划、材料清单的同一份材料

送交材料含 `deal`。§7.2 的构造计划座位项不含 `deal`。

在版本 2 上，构造计划里每一座位项的 `materials`，必须与本载荷中该手、该用途、该座位的条目在 `purpose_label`、`index_key`、`value` 上逐项相同，次序都符合 §7.3 与 §9.3：被测臂的被测座位只含那一条 `arm_m`；基线臂的被测座位只含该手的 `arm_b` 切片；两臂的非被测座位是同一组 `non_probed`。缺一条、多一条或整数不同，两份摘要不能同时被接受。

材料清单仍是 `74r` §8.3.7 的扁平数组，字段名仍是 `purpose_label`、`index_key`、`value`，不加 `schema`。版本 2 的清单使用 §9.2 的键形，次序仍是 `74am` §9：用途遍历顺序，用途内完整键升序。同一份材料在清单与送交材料里的键和整数必须逐项一致；清单按全局次序摊平，送交材料按手分组。两个摘要不同是预期，不得混同。本文件不改 `74r` §8.3.7 的正文。

实际材料的字节只在 ⑥ 产生。③ 只用非实际材料夹具核验本节的结构、键形、条数与排序。
