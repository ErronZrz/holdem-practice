## 4. 主随机值

提案构造如下。锁定文本采用之前，生成过程不得改按这一节执行。

| 项 | 提案 |
|---|---|
| **长度** | `32` 字节，即 `256` 位 |
| **来源** | 仍是 `python-os-urandom@1`。不更换这一标识 |
| **次数** | 一次材料生成过程只读取这一次，作为该次生成的唯一主值。不是每手一次，也不是每个 κ 一次 |
| **次序** | 串行，且在任何派生之前。若 §6 的某一选项仍让 `deal` 或 `arm_m` 直接读外部随机，那些读取排在这一次之后，接在同一条原始字节转录上 |
| **逐读取记录** | 八个字段名不改。这一次的 `read_index = 0`，`purpose_label = master`，`index_key` 只有 `campaign`，`bit_width = 256`，`raw_offset = 0`。`raw_value` 与 `output` 都是这 32 字节的无符号大端整数，`accepted` 为真 |
| **注入** | 仅限非实际夹具。夹具传入 32 字节时不调用 `os.urandom`，派生种子由该字节串确定。实际材料生成必须调用 `os.urandom(32)`。实际路径上传入主值则硬失败，不得把注入值记成 `python-os-urandom@1`。来源标识只记在实际路径的那一次 `os.urandom` 上。派生出的各个种子不再单独注入 |
| **承诺字段** | 仍是 `74r` §6.6 的 **14** 个字段名。主值写在逐读取记录里，因此进入 `audit-read-record-digest` 与原始字节转录。**不**新增 `master_random_digest`。把主值摘要再单列成第 15 个承诺字段，不是本提案的做法 |
| **遍历标签** | `traversal_order` 在 `deal` 之前增加 `master`。`entry_counts` 与 `rejection_counts` 按这个加长后的次序排列。变的是这两个数组的内容，不是 14 个字段的名字 |

`master` 的 `campaign` 必须等于 §9 以 `randomization_protocol = 3` 重算的配置摘要。本提案不算出该摘要，也不写下任何 32 字节实例。

`entry_counts` 里 `master` 的条数是 `1`，`rejection_counts` 里这一标签是 `0`。域是 `2^256`，这一次读取的拒绝区间为空。

## 5. 派生函数

### 5.1 构造

提案采用带域分隔的 HMAC-SHA256。

| 项 | 提案 |
|---|---|
| **算法标识** | `hmac-sha256-domain-separated-v1`。编码或算法有变时，这一标识必须换，不能沿用同一字符串配另一套字节 |
| **域标签** | `kappa-seed-derive-v1`。它只出现在消息里，不是协议载荷的 schema 名 |
| **HMAC 的键** | §4 那 32 个原始字节。不用十六进制，也不用十进制 |
| **HMAC 的消息** | §5.2 的字节串 |
| **输出** | HMAC-SHA256 的 32 字节，`raw_value = int.from_bytes(digest, "big", signed=False)`。因而 `0 ≤ raw_value < 2^256` |

材料单元仍是这个整数的 32 字节无符号大端。同一整数只有一种这样的字节串。`samples` 与 `bluff_freq` 不进入消息，也不进入这 32 字节。

### 5.2 无歧义编码

消息是字段的顺序拼接。每个字段先写 4 字节无符号大端长度，再写 UTF-8 载荷。长度只数载荷，不含长度字本身。字段之间没有别的分隔符。不用 JSON，不出现浮点。

六字段用途（`non_probed` 与 `arm_b`）的字段顺序：

| 顺序 | 载荷 | 约束 |
|---|---|---|
| 1 | `kappa-seed-derive-v1` | 逐字相等 |
| 2 | 用途标签 | 只允许 `non_probed` 或 `arm_b` |
| 3 | `campaign` | 恰好 64 个小写十六进制字符，长度字为 `64` |
| 4 | `block` | 规范十进制：无前导零，`0` 写作 `0` |
| 5 | `hand` | 同上 |
| 6 | `seat` | 同上 |
| 7 | `event_index` | 同上 |
| 8 | `sigma_public` | `74am` §6.4 的小写十六进制字符串。长度字等于该字符串的字符数，不是解码后的字节数 |

用途标签放在键字段之前，避免同一 κ 在两种用途下得到同一消息。`campaign` 放进消息，避免两个战役共用主值时得到同一消息。校验方用已经提交的字符串重算，不调用 `EncodeK2PublicV1`。

`deal` 与 `arm_m` 的消息字段表不在这里写死。只有 §6 选定连这两用途一起派生时，才由那时的锁定文本补字段表。

### 5.3 映射与拒绝标识

对 `D = 2^256`、位宽 `w = 256`：

```text
B = D · ⌊2^w / D⌋ = 2^256
raw_value 总是 < B
输出 = raw_value % D = raw_value
拒绝区间 [B, 2^w) 为空
```

因此这两类派生**不再做拒绝采样**，也不为同一 κ 计算第二次 HMAC，更不为此再读 `os.urandom`。

这仍是 `rejection-whole-multiple-truncation-v1` 那条公式在 `D = 2^w` 上的推论，与 `74am` §10 对 `non_probed`、`arm_b` 已写的空拒绝区间同一关系。本提案**不改**该标识所指的接受公式、输出 `raw_value % D`、以及「仅 `[B, 2^w)` 被拒绝」。标识因此保持不变。

若将来的锁定文本把「拒绝后继续读取」改成「拒绝后更换消息再派生」，那是规则内容的改变，标识必须换，并以新的 `74` 后缀承接。§6 的全用途选项会碰到这件事；本提案在该选项未被选定前不换标识。

**新增**：每条记录的字段集合恰好是 `purpose_label`、`index_key`、`value`。这是上表「至少含」的三项，本文件把集合收成恰好这三项。`purpose_label` 只许 `non_probed` 或 `arm_b`。`index_key` 是六个字符串，顺序与 `74am` §6.1 相同。`value` 是 `[0, 2^256)` 内的 JSON 整数。多字段、缺字段、别的用途或域外整数都失败。

**新增**：每个键还要满足 `74am` §6.1、§6.2 与 §6.4 对这两用途的字段规则。不把 §6.3「闭合集里至多一条投影」用到决策记录上；§6 与 §14 已经写明该条不再约束这两用途。同一 `purpose_label` 加六个字符串再次出现即失败。至少包括：

| 字段 | 规则 |
|---|---|
| `campaign` | 等于 §9 以 `randomization_protocol = 3` 重算的配置摘要 |
| `block` | 规范十进制，等于该次运行规格的块序号 |
| `hand` | 规范十进制，且落在该次手序计划内 |
| `seat` | 规范十进制，且在 `0 … N−1` 内。`arm_b` 的座位必须等于该手被测座位。`non_probed` 的座位不得是该手被测座位 |
| `event_index` | 规范十进制 |
| `sigma_public` | 满足 `74am` §6.4：小写十六进制，偶数长度，字母表只含 `0123456789abcdef` |

规范十进制与 `74am` 相同：无前导零，`0` 写作 `0`。键不合法时，即使 HMAC 输出与 `value` 相等，核验也失败。

**新增**：包内核验由 `verification` 执行，时点是决策记录已经提交之后，不是运行前冻结。它只核对已经提交的记录：上列键规则，以及 `value` 等于用已提交主值按 §5 重算的 HMAC 输出。编排器按 §5 算出整数并注入；编排器的这次计算不是核验。校验包不调用 `EncodeK2PublicV1`，不创建引擎，不提交行动，不推进牌局。不等或键不合法即协议失败，停止，不补读外部随机。

**新增**：完整性对账不在包内做。校验包看不到对局里实际发生过哪些注入，因此不能判断「发生了注入却没有记录」。这条核对由 ⑦ 运行产生的对局日志与决策记录逐条对账，在包外完成。时点是该次 ⑦ 已经写出对局日志之后。对象是日志里的每一次派生用途注入，与决策记录的完整键。它不属于冻结身份，也不属于包内校验。本文件不授权 ⑦，也不把对账写成已经发生。

**新增**：已知限制有两层。运行前冻结身份不证明派生整数已被核验。冻结清单里的那两份摘要只绑定规则与主值。K-5 在 `non_probed` 与 `arm_b` 上三方都缺席，缺席不是已经核验。另一层是：记录缺失无法由包内发现；包内只看见已经提交的记录。

| **金额** | 派生输出是种子整数，不是筹码。筹码仍用既有的单一整数单位 |
| **N 人** | `seat` 与 `event_index` 是规范整数。编码不把人数写成 2 |
| **`verification`** | 可配置且不可执行。重算只使用已提交的主值字节与已提交的字段字符串，做长度前缀与 HMAC。不引入引擎，不推进牌局，不生成材料，不调用公开投影 |
| **包外** | 生成器只读一次主值。编排器在决策前取得投影，再计算种子，然后 `create_strategy("heuristic@1", seed=该整数)`。缺主值或编码失败则停止，不回调生成器补料 |
| **依赖** | `poker/` 不依赖 `api/` 或 `llm/`。`strategy/` 仍只经 `GameState` 与 `poker/` 交互。不修改 `HeuristicStrategy` 来完成注入 |

**逐字**（`74au` §14）：

协议能够证明的只有确定性与可复核：同一主值与同一消息得到同一整数；第二遍计算与记录一致；消息不同则输入不同。

它不证明主值来自独立均匀的源，不证明 `os.urandom` 的实现满足均匀，也不证明不同 κ 上的种子作为随机变量互相独立。HMAC 是确定函数。输入不同时期望输出不同，这不是均匀性或独立性的证明。

这一界限延续 `74am` 保留的「协议不证明真实独立性」。版本 3 不把「可以重算」写成「已经独立」。
